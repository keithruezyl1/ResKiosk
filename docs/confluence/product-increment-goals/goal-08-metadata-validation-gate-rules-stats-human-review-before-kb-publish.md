# Goal 8: Metadata validation gate (rules + stats + human review before KB publish)

### 1) Outcome

Implement a **metadata validation gate** so autogenerated captions/labels (especially for multimodal KB items) are **verified, auditable, and safe** before they affect resident-facing retrieval.

* **What changes**: KB publish is gated by a validation pipeline that classifies metadata as **approved** vs **quarantined**, with optional offline/batch LLM support for review (not in the hot path).
* **Who benefits**: residents (safer, more reliable filtering), admins (clear review queue), maintainers (reproducible KB versions with auditable metadata quality).
* **What success looks like**:

    * low-confidence / rule-failing metadata is blocked from publish (or excluded from resident retrieval) until reviewed
    * review decisions are recorded and traceable to a KB version
    * validation outputs (rules + stats) are inspectable and consistent for the same KB snapshot/config
    

---

### 2) Why this matters

* **Current limitation**: there is **no formal publish gate** for autogenerated metadata/captions.
* **Risk addressed**: bad metadata breaks Goal 7 filtering/scoping and increases risk for **medical/safety** content (incorrect exclusion/inclusion).
* **Value**: a gate converts “best-effort metadata” into **trusted, versioned retrieval constraints** and creates an auditable workflow for human oversight.

---

### 3) Scope

* Define validation **rules + statistical checks** for autogenerated metadata, at minimum covering:

    * captions (text quality + safety checks)
    * labels/taxonomy assignments (Goal 7 taxonomy IDs) and their confidence/coverage
    
* Implement a **quarantine vs approved** workflow tied to KB publish:

    * items that fail rules/stats are quarantined for review
    * only approved metadata is allowed to influence resident-facing filtering/retrieval
    
* Provide an **admin review surface** (minimum viable) to:

    * view failures and supporting evidence (rules triggered, stats outliers)
    * approve/reject/override with reason codes
    * track audit history and link decisions to KB version
    
* Implement an **offline/batch** LLM-as-judge hook (optional) to assist review:

    * produces recommendations/flags for humans
    * never blocks the kiosk/hub hot path
    

---

### 4) Non-goals

* Running LLM-as-judge inside the resident request path (hot path).
* Fully automated “no-human” publishing for high-risk metadata.
* Building a full-featured annotation platform (multi-user workflows, rich diffing, etc.).
* Rewriting or re-chunking KB content (retrieval unit remains a KB row per global assumptions).

---

### 5) System Impact

#### a. Data / Schema

**New concepts (minimum viable)**

* **Validation status** for metadata (per KB item, per metadata bundle):

    * `approved | quarantined | needs_review | rejected` (exact set is an implementation detail; semantics below are authoritative)
    
* **Validation results** persisted for auditability:

    * rules fired (IDs), severity, messages
    * statistical checks (feature values + thresholds + pass/fail)
    * model provenance for autogenerated fields (e.g., captioner/labeler version) when available
    
* **Review outcomes**:

    * reviewer identity, timestamp, decision, reason code, notes
    * link to KB version/publish attempt
    

**Relationship to Goal 7 metadata**

* Validation explicitly targets metadata fields used by filtering policy (Goal 7), including taxonomy node assignments and any authority/scope fields.

#### b. API / Interfaces

* **Publish flow** (admin/console → hub):

    * publish must call/trigger validation and receive a clear gate outcome: `pass | blocked` plus a summary of quarantined items.
    
* **Admin review**:

    * endpoints (or internal calls) to list quarantined items, fetch validation details, and apply review decisions.
    
* **Retrieval** (hub internal):

    * resident-facing retrieval must treat quarantined/unapproved metadata as **not eligible for enforcement** (see policy below), while hard rules still apply.
    

#### c. UX / Behavior

* **Admin**:

    * a clear “ready to publish” indicator vs “blocked by validation”
    * a review queue with filters (severity, taxonomy, modality, source)
    
* **Resident (kiosk)**:

    * no new UI required; safety benefit comes from preventing bad metadata from shaping filters.
    

---

### 6) Integration Points

* **Depends on**:

    * Goal 7 (metadata schema + filtering policy): defines which fields matter and how mistakes can cause harm
    * KB publish/versioning (KB version must be the anchor for auditability and reproducibility)
    
* **Affects**:

    * Goal 4/5 (hybrid + multi-path): retrieval behavior depends on validated metadata constraints
    * Goal 10 (metrics/logging): validation and review events should be measurable per KB version
    * Goal 11 (caching): publish-time changes must invalidate caches and must not serve data based on unapproved metadata
    

---

### 7) Edge Cases / Failure Modes

* **Validation system down / unavailable**:

    * publish must fail closed (block) for new KB versions, or require an explicit “emergency override” that is auditable (see policy).
    
* **High quarantine volume**:

    * provide deterministic batching and severity sorting so admins can clear the queue efficiently.
    
* **Conflicts between human overrides and rules**:

    * allow overrides but require a reason code and log the rule(s) overridden; do not silently discard validation outputs.
    
* **Taxonomy drift / missing mappings**:

    * do not auto-create taxonomy nodes; quarantine items with unmapped/unknown taxonomy IDs.
    
* **Multimodal mismatch** (caption doesn’t describe image / label mismatch):

    * quarantine with a specific mismatch code; optional offline LLM judge may assist but cannot auto-approve without human review (minimum viable safety stance).
    

---

### 8) Logging & Metrics

Log enough to audit and measure gate quality per KB version:

* validation run:

    * KB version (or publish candidate ID), run timestamp, rule IDs fired, stats checks results
    * counts: total items validated, quarantined, approved, rejected
    * breakdown by modality and taxonomy main category
    
* review workflow:

    * reviewer decision events (approve/reject/override) with reason codes
    * time-to-approve, backlog size over time
    
* publish:

    * publish blocked vs passed, with quarantined summary
    

---

### 9) Determinism / Constraints

* **Deterministic validation**: for a fixed KB snapshot and fixed validator configuration, rule/stats outcomes should be reproducible.
* **Safety constraints**:

    * resident-facing retrieval must not rely on quarantined/unapproved metadata to enforce scoping
    * any publish override must be explicit, logged, and traceable to an operator identity
    

---

### 10) Definition of Done (DoD)

* Validation rules and statistical checks are defined and implemented for autogenerated captions/labels (minimum viable).
* Validation produces a clear per-item status and persists auditable results.
* KB publish is gated: quarantined items block publish (or are excluded from resident retrieval) according to the policy below.
* Admin workflow exists to review quarantined items and record decisions tied to KB version.
* Optional offline/batch LLM-judge hook exists as a non-hot-path assist (can be disabled without breaking the gate).
* Logs/metrics exist to measure quarantine rate, approval latency, and publish-block reasons.

---

### 11) Open Decisions

* Exact schema location for validation artifacts (new tables vs JSON metadata on KB items) while keeping queries simple for the admin queue.
* Gate semantics: “block publish until cleared” vs “publish but exclude quarantined items/fields from resident retrieval” (recommended default: block for high-risk categories).
* Minimum viable rule set and thresholds (especially for medical/safety content) and how to tune them without breaking determinism.

---

## Policy / Rules

### Gate policy (authoritative)

* **Default**: if validation finds quarantined items for resident-facing retrieval metadata, **publish is blocked** until reviewed.
* **Allowed alternative (only if needed for operational continuity)**: publish can proceed, but quarantined metadata must be treated as **inactive for enforcement** in resident retrieval (i.e., do not narrow/shape filters based on it), and the console must display a prominent “published with quarantine” warning. This path must be fully auditable.

### Rule categories (minimum viable)

* **Taxonomy integrity** (Goal 7):

    * taxonomy node IDs must exist and be valid
    * multi-assignment rules enforced (primary required; secondary optional)
    
* **Authority/scope integrity** (if used by filtering):

    * values must be within the allowed enums; missing values are quarantined when required by policy
    
* **Caption sanity** (for image assets / multimodal items):

    * must be non-empty, language-valid at the retrieval boundary (English), and free of prohibited patterns (e.g., placeholders, obviously irrelevant boilerplate)
    
* **Safety-critical checks**:

    * medical/safety taxonomy items require stricter thresholds and mandatory human approval on first publish (exact thresholding is an open decision, but the presence of this stricter regime is required)
    

---

## Workflow / Review States

### States (suggested minimum viable)

* `approved`: eligible for resident-facing enforcement (filtering/scoping)
* `quarantined`: blocked pending review; not eligible for enforcement
* `rejected`: explicitly rejected; must be corrected (human edit or regeneration) before approval

### Transitions

* `quarantined` → `approved` (human approve)
* `quarantined` → `rejected` (human reject)
* `rejected` → `quarantined` (after correction/regeneration + re-validation)

All transitions must be logged with a reason code and reviewer identity.

---

## Evaluation / Benchmark Plan (recommended for Goal 8)

* Track quarantine rate overall and by taxonomy main category (Goal 7) and modality.
* Sample-based audit:

    * randomly sample approved items per KB version and verify correctness
    * targeted sampling for medical/safety categories
    
* Measure operational metrics:

    * time-to-approve, review backlog size, top failure rule IDs
    * publish-block frequency and reasons
